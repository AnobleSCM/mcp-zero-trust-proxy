How it works

Everything you need.
Nothing you don't.

One proxy. Full zero-trust security. No server code changes.

🔐

OAuth 2.1 Authentication

Require login before anyone can use your tools. Works with GitHub, Google, Okta, or any OIDC provider — using the latest OAuth 2.1 PKCE standard.

🛡️

Tool-Level Access Control

Decide who can do what. Give one team full access, restrict another to read-only, block specific tools entirely — all configured in a simple YAML file.

🔒

Per-Client Sessions

Every user gets their own walled-off session. One client's data never leaks to another — even if they're using the same upstream server.

📋

Structured Audit Trail

Every request is recorded — who made it, what they asked for, whether it was allowed. Structured JSON logs with file rotation for security reviews.

⚡

Quick Setup

Docker pull, set your MCP target and auth provider, done. Single container, single config file. No Kubernetes required. Sub-millisecond overhead.

🚦

Per-Client Rate Limiting

Prevent any single user or agent from overwhelming your server. 300 req/min default, configurable per client with token-bucket enforcement.

FAQ

Common questions

What if Anthropic adds native auth to the MCP spec?
That would be great. Native auth solves authentication. The proxy continues to add value for what comes next: authorization (who can call which tools), structured audit logging, per-client rate limiting, and per-client sessions. The MCP spec has no plans to standardize these — and for regulated environments, they are not optional.
Is my traffic or data sent to any cloud service?
No. The proxy runs entirely on your own infrastructure. Your MCP traffic, tokens, and audit logs never leave your servers. The only external dependency is your OAuth provider (GitHub, Google, etc.) for the authentication flow — which your users already trust.
Why not just use Caddy + Authelia or nginx + OAuth2 Proxy?
Generic reverse proxies don't understand the MCP protocol. They can authenticate users, but they can't enforce which MCP tools a user is allowed to call, isolate per-client sessions within the MCP connection, or produce structured audit logs per JSON-RPC method. This proxy was built specifically for MCP's JSON-RPC 2.0 over HTTP+SSE transport.
How do rate limits work across replicas?
Rate limits are per-instance in v1.0. If you run multiple replicas behind a load balancer, each enforces its own limits. For strict global rate limiting across replicas, a shared Redis store (planned for v1.1) would be needed. For most single-server deployments, per-instance limiting is sufficient.
